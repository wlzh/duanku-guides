## 正文

搜 InstaBox 邀请码的人，大多已经走到了登录那一步，页面停住了，不知道自己是该等，还是该换个办法。

主教程里把这一步写得很短。打开 instabox.sh，用 Google 账号登录，注册后等待邀请码，收到邀请后就可以体验。短是短，卡住的人恰恰卡在这句“等待”上。等多久算正常，没收到算不算失败，要不要换账号重来，主教程没有展开，这篇就展开这部分。后半篇再讲拿到邀请之后怎么用，命令行、SDK 和 GitHub 项目都给你摆出来，免得你拿到一台机器却不知道从哪下手。

## 邀请制是什么意思

InstaBox 现在是一个邀请制内测的云服务，主打给 AI Agent 提供云端运行环境。邀请制的意思是，注册不等于立刻开通。系统要先确认你的账号，再放你进去。

这里先分清两种结果。一种是登录后直接进去，不需要再等。另一种是登录后进入等待，收到邀请后才能体验。两种结果在主教程里都出现过，主教程记了一句，有的 Gmail 账号年份高，是直接登录成功了，不需要邀请码。

这句话要小心着读。它是主教程里的一次观察，不是官方公布的规则。主教程没有说年份高到多少算高，也没有说新账号一定会被拦下来。把“老号直接进”当成规律，再去买老号或者借别人的老号登录，风险就落到自己头上了。账号是自己的，登录记录也是自己的，出了问题没人能替你兜。

同样，邀请码也不是一个可以到处找的通用码。主教程没有提供任何公开的邀请码，这篇也不会提供。网上有人卖码，有人说可以代注册，这些说法都没有官方背书。码的来源不明，账号交到别人手里，本身就是一次风险。

## 等多久，有几种说法

主教程里作者自己的那次，是一天后收到的。主教程还记了一句反馈，有人上午申请，下午就收到了邀请。这两种说法放在一起，意思其实很清楚。等待时间不是固定的，有人快，有人慢。

主教程没有给出官方的时间表，也没有说超过几天就等于被拒绝了。所以这篇不给你一个“等三天必到”之类的承诺。任何人跟你说“保证当天到”“保证三天到”，那都是他自己的说法，不是 InstaBox 公布的规则。

等待的时候，最容易犯的错是反复折腾。换一个邮箱重新注册，换一个浏览器重新登录，一天之内来回试几次，看起来是在推进，其实是在给自己加变量。系统认的是你第一次注册的账号。换账号等于换了一个排队的人，原来那个账号的状态反而更难查了。

如果你已经注册了，先稳住一个账号。隔一段时间，用同一个账号重新登录 instabox.sh 看一次状态。能直接进去，等待就结束了。还是停在等待，说明还没轮到你，不是你操作错了。

## 没收到，先按这个顺序查

第一步，确认账号没有换。你现在登录的 Google 账号，必须是你当初注册用的那个账号。很多人同时登着好几个 Google 账号，浏览器右上角看着是一个，实际提交的可能是另一个。先到右上角核对一遍，再谈下一步。

第二步，用同一个账号重新登录一次。直接进去，就不用再等了。还是等待页面，就记下你现在看到的页面状态，不要急着换号。

第三步，回想一下注册时间。刚注册不到一天，没收到是很常见的。主教程里作者自己就等了一天，有人当天收到，也有人等更久。时间短，先等，不要因为焦虑就去买码。

第四步，别做的事要先划出来。不要买邀请码，也不要找人代注册。账号和验证码更不能交给别人，借别人的账号来赶时间同样不行。这些做法一旦出问题，损失的是你自己的账号和数据，不是卖码的人。

第五步，想清楚这台机器现在能用来干什么。InstaBox 还在内测，免费政策能持续多久，主教程里已经提醒过，尚不明确。就算你今天拿到了邀请，也别急着把重要业务部署上去。先拿它跑跑脚本，部署个轻量服务，看看闲置暂停、快照和端口这些机制是不是合你的习惯，再决定要不要长期用。

## 几种说法，为什么不能信

“老号一定直接进”，不能信。主教程只记了一次观察，没有给出年份门槛，也没有说所有老号都免邀请。

“换个邮箱一定更快”，不能信。换邮箱等于换一个账号重新排队，原来那个账号的等待并不会因此变快。

“买个码就能立刻用”，不能信。码的来源、有效期、会不会连坐封号，主教程和官方页面都没有说明。花钱买一个不确定的东西，换来的往往是更多的不确定。

“等不到就是被拒绝了”，也不能直接下结论。主教程没有公布拒绝的通知方式，也没有公布等待上限。没收到，不等于被拒绝，只能说还没轮到。

## 拿到邀请之后，先核对你的免费额度

动手之前，先把一个容易踩的坑说清楚。主教程写于 10 月 18 日，那时说最多开 5 台，总计 20 核加 40GB 内存。官方文档现在写的是另一套口径，免费档是 1 台机器、5 个快照、200GB 存储总量，单台 4 核加 8GB，20GB 持久盘，闲置 30 分钟自动暂停，最长连续运行 480 分钟。

这两套说法打架，不代表谁在撒谎。早期内测用户确实拿到过 5 台，后来的免费档收紧了。你的账号到底是哪一种，不要听文章的，去你自己的账号用量页面看一眼。那里写几台就是几台，写几个快照就是几个快照。按 5 台去规划，结果发现只能开 1 台，脚本和快照的安排全要重来。

免费档还有几个边界，拿到邀请那天就要先对一遍。机器是 Debian 13 的 Firecracker 微型虚拟机，预装了 Docker、Node.js、Python、Go、Rust、OpenJDK 21，还有带 Chromium 的桌面环境，Claude Code 和 Codex 也已经装好了。持久数据在 20GB 的 /data 盘上，家目录在 /data/home 里，/tmp 是内存盘，大文件别往 /tmp 里塞。出网 TCP 和 UDP 都通，入网没有独立的 IPv4，只能走官方的 HTTPS 网关或者 SSH 网关。这句话翻译过来就是，它是一台给 Agent 干活的工作台，不是用来替代年付 VPS 的。想拿它挂一个 24 小时在线、还要绑定自己域名的网站，这条路本身就不通。

闲置暂停也要先接受。免费档的 30 分钟是固定的，官方文档说免费档改不了这个值，关掉自动暂停是付费档的选项。主教程里提过 CLI 的自动暂停参数，那个参数在免费档上不是你想改就能改的。暂停后恢复很快，内存状态还在，但它不是一台永远在线的机器。按这个节奏去用，跑脚本、跑测试、跑 Agent 任务都很顺，按永远在线去用，第一天就会失望。

## 拿到邀请之后，怎么用

最快的一条路是一条命令。官方文档给的起手式是 npx instabox@latest sh，这条命令会登录，装好命令行工具和 Agent 技能，再开一台机器并连进去。如果你只想先装工具不想马上开机器，就用 npx instabox@latest，或者用 npm install -g instabox 只装命令行工具。

进了机器，日常就这几条命令，够你把一台机器跑起来。

```
npx instabox@latest sh
instabox create --name work
instabox exec work -- uname -a
instabox ssh work
instabox port publish work 3000
instabox snapshot save work --name work-ready
instabox create --name work2 --snapshot work-ready
instabox suspend work
instabox resume work
```

这几条命令按顺序读一遍，整套玩法就清楚了。create 是开机器，exec 是在机器里跑一条命令，ssh 是连进去自己动手，port publish 是把机器里的 3000 端口变成一个公开的 HTTPS 链接，snapshot save 是把当前状态存成快照，create 加 snapshot 是从快照再开一台一样的机器，suspend 和 resume 是暂停和恢复。

有几个用法，值得你拿到邀请后第一周就试一遍。第一个是快照当模板用。先把一台机器配到你顺手的状态，装好你要的工具，写好常用的配置，存一个快照。以后每次开新机器都从这个快照起，不用每次重装。第二个是 setup 文件和开发容器。create 的时候可以带一个 setup 文件，最多 64KB，机器一启动就按文件里的脚本跑一遍。也可以直接从 devcontainer.json 起，工作区、环境变量和生命周期命令都按那个文件来。第三个是把仓库搬进去。在机器里 git clone 自己的仓库，跑测试，跑构建，跑完把结果拉回来。机器用完就删，快照留着，下次还能从同一个状态继续。

如果你想让 Agent 自己去用这台机器，就不要只停留在命令行。官方给了 TypeScript SDK，装法是 npm install @insforge/instabox-sdk，Python 也有对应的包，装法是 uv add instabox。SDK 能做的事和命令行是一套，建机器、跑命令、读写文件、暂停恢复、存快照、发端口、拿 SSH 凭证，都能用代码调。API 密钥在控制台的 API Keys 页面建，也可以用 instabox keys create 建，密钥只显示一次，建完就要自己存好。调 API 的时候，密钥放在 X-API-Key 请求头里，或者放在 Authorization 的 Bearer 令牌里。

密钥这件事要单独提醒一句。给 Agent 用的密钥，最好按作用域建。官方文档里写得很清楚，密钥可以只给读权限，也可以给写和删的权限。你只想让 Agent 跑命令和读文件，就不要给它删机器的权限。密钥一旦交出去，权限就是按密钥算的，不是按你嘴上说的算。还有一条硬规则，删机器和删快照的时候，API 要求带一个确认请求头，值是机器的编号或者准确的名字，带错了会直接返回 409，什么都不会删。这条规则是保护你的，删之前多看一眼名字。

还有一个很多人会忽略的点，命令的输出是有上限的。官方文档说，不用流式输出的时候，每条输出流最多截到 1MB，二进制内容会被替换成占位符。跑大输出的命令，最好用流式输出，或者直接把结果写到文件里再拉回来。上传速度也有上限，官方文档写的是每台虚拟机大约 50 Mbit 每秒，100MB 左右的文件传上去要十几二十秒。大文件用 instabox cp 或者 push 走 HTTP 并行传，不要用 scp 或者 rsync 慢慢磨。

## GitHub 上玩这台主机的项目

官方工具之外，GitHub 上已经有几批人在围着 InstaBox 做东西。下面这几个是我查到的项目，确实跟 instabox.sh 这台主机有关。先讲清楚哪些是官方的，哪些是社区的，免得你装错。

第一个是 igzard 的 instabox-skill，链接是 https://github.com/igzard/instabox-skill 。这是一个教 Claude Code 这类 Agent 怎么用 InstaBox 的技能包，里面讲了命令行、生命周期、端口、SSH、快照、密钥库、API 密钥和额度限制，还带了 TypeScript SDK 和 HTTP API 的参考。装法是 npx skills add igzard/instabox-skill，或者在插件市场里加。注意，这个项目由社区维护，内容以官方文档为准，技能和文档打架的时候，听文档的。

第二个是 syrex1013 的 instabox-mcp，链接是 https://github.com/syrex1013/instabox-mcp 。这是一个 MCP 服务器，把 InstaBox 的 REST API 包成了 30 个工具和 6 个快捷命令，让 Claude、Codex、Antigravity、Cursor 这些客户端可以直接建机器、跑命令、改文件、存快照、发端口、删机器。它也标明了自己是非官方项目，没有得到 InstaBox 的背书。用它之前，先在控制台建一个带合适作用域的 API 密钥，密钥的环境变量名字是 INSTABOX_API_KEY。它的只读模式可以把所有会改动的工具关掉，先用只读模式试一遍，再决定要不要放开写权限。

第三个是 forge-z 的 pi-agent-telegram，链接是 https://github.com/forge-z/pi-agent-telegram 。这是一个跑在 Telegram 里的个人 AI 助手，一个容器加一个数据卷，没有网页面板。它通过一个统一的工具端点去接各种服务，InstaBox 在里面是作为一个 Linux 沙箱工具出现的，可以跑真实的命令行、用浏览器、读写持久盘、跑代码、构建和发布产物。它的文档里还写着免费档 5 台。官方文档现在写的是 1 台，这个数字打架，你用的时候以自己账号的用量页面为准，不要按它的文档去规划机器数。

第四个是 lizhenmiao 的 instabox-keepalive，项目介绍页在 https://reporank.net/en/repo/lizhenmiao-instabox-keepalive.html 。这是一个单文件的 Cloudflare Worker 面板，用来管 InstaBox 的机器和账号，可以看状态、做生命周期操作、看日志，还能按定时任务去续一个活动租约。部署要配 Cloudflare Worker、定时触发器和 Upstash Redis，租约本身只有 3600 秒，所以续租全靠定时任务一直跑。这里要把话说死，这个面板不能去掉平台的限制，也不能保证机器一直在线。它续的是活动租约，不是把免费档变成付费档。指望靠它把一台免费机器变成 24 小时在线的服务器，是走不通的。

还有一批名字很像、但完全不是这台主机的项目，搜的时候最容易装错。onedebos 的 instabox-rails-API 是一个 Instagram 克隆的后端，Linguista 的 CQPweb-Instabox 是装 CQPweb 服务器的脚本，tmibvishal 的 instaBox 是一个 Instagram 工具包，下载头像、拼九宫格那种。名字里都有 instabox，但跟 instabox.sh 没有关系。搜 GitHub 的时候，先看项目介绍里有没有写 instabox.sh、API 地址是不是 api.instabox.sh，再动手 clone。

官方自己的东西也别漏掉。官方文档在 https://instabox.sh/docs ，给 Agent 读的精简版在 https://instabox.sh/llms.txt ，API 文档在 https://instabox.sh/docs/api.md 。命令行工具的 npm 包在 https://www.npmjs.com/package/instabox ，TypeScript SDK 的包名是 @insforge/instabox-sdk，Python SDK 在 https://pypi.org/project/instabox/0.1.0/ 。还有一篇第三方实测，VPSDEX 的 InstaBox 免费档评测，链接是 https://vpsdex.com/en/activity/instabox-free-cloud-server-for-ai-agents-review/ 。它把官方数字和第三方观察分开标了，读的时候能帮你分清哪些是官方说法，哪些是别人测出来的。

## 拿到邀请之后，先做这几件事

第一件是核对额度。去账号用量页面看一眼，几台机器、几个快照、多少存储，按那个数字规划，不要按主教程里的 5 台规划。

第二件是留好退路。内测阶段的免费服务，政策随时可能变。重要数据要有自己的备份，重要服务要有能迁移的地方。机器是免费的，数据丢了可不是免费的。

第三件是先跑一遍最小一整套流程。开一台机器，跑一条命令，发一个端口，存一个快照，再从快照开一台新的，最后把旧机器删掉。这套流程跑通了，你才算真的会用这台机器，后面接 Agent、接 SDK、接 GitHub 项目，都是在这套流程上加东西。

## 写在最后

邀请码这件事，难的是等待的时候心里没底。有人直接进，有人等了一天才收到，也有人等得更久。把它们放在一起看，结论其实很简单。用自己的账号注册，等一等，隔段时间用同一个账号回来查一次，别买码，别代注册，别换号折腾。

如果你现在正卡在等待页面，先做上面那五步里的第一步和第二步。账号核对清楚，重新登录一次，能进就进了，进不去就再等一等。等的过程中，把主教程里的配置和边界先读一遍，拿到邀请那天，你就不用再从头摸索了。
